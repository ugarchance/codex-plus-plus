9. Computer Use / `cua_repl` reported "Sky Computer Use native pipe startup failed" (2026-09-09). Measurement: `~/Library/Logs/DiagnosticReports` held 15 `codex-code-mode-host` crashes that day, parent `codex` app-server, SIGTRAP inside `v8::internal::IsolateGroup::EnsureCodeRange` → `FatalProcessOutOfMemory`. The stock binary carries `com.apple.security.cs.allow-jit` and `allow-unsigned-executable-memory`; the installer had re-signed it with `--options runtime` and no entitlements, so V8 could not map executable memory. Reproduced the mechanism with the bundled `cua_node/bin/node`: signed the same way it dies with "Failed to reserve virtual memory for CodeRange" (exit 133), signed with the entitlements file it runs. Fix: `sign_helpers` in the installer and the `resign` subcommand. The exact message text is not in the asar or the binaries' printable strings; the app's own `computer-use native pipe startup failed` log line is Windows-only.
10. After the re-sign the mock-provider turn still logged `dynamic_app_tools_peer_rejected reason=missing-code-signing-identity` three times. The pipes are created with mode 0600.

12. Native `cua_repl` (the on-screen surface: `cua.getState`, screenshots, clicks) reported "Sky Computer Use native pipe startup failed" after items 9–11 (2026-09-09). **Root cause: the installer stripped the OpenAI Developer ID signature off `Resources/codex`. Fix: keep `codex` (and `codex-code-mode-host`) Developer ID signed — do not re-sign them ad-hoc.** This needs no change to the external service, no binary patch, and no anti-debug work, and it also subsumes the item-9 JIT fix.

    How it was found. The native UI surface is gated by an **external** service, `SkyComputerUseService` inside `~/.codex/computer-use/Codex Computer Use.app` (shared with stock ChatGPT, launched on demand, self-exits when idle; the client `Resources/cua_node/.../targets/mac/native-pipe.js` connects to `~/Library/Group Containers/2DC432GLL2.com.openai.sky.CUAService/IPC/computeruse.sock`). The service authorizes a connection by its peer's process **ancestry**, read from the audit token via `SecCodeCopyGuestWithAttributes` + `SecCodeCopySigningInformation` / `kSecCodeInfo{Identifier,TeamIdentifier}` (no `SecCodeCheckValidity`): it needs a signer with **team `2DC432GLL2`** somewhere above the peer, else `relay_without_trusted_ancestor` and an accept-then-close. Comparing the live trees confirmed it: stock ChatGPT's CUA `node_repl` and Codex++'s are the *same* Developer ID binary (team `2DC432GLL2`), and the **only** difference is the ancestors — stock has `com.openai.codex` / `codex` (Developer ID, team `2DC432GLL2`), Codex++ had ad-hoc `codex` → ad-hoc `Codex++-bin`. A framed-JSON-RPC `ping` probe nailed the rule empirically: launched directly under a shell it is rejected (accept+close), but launched as a child of any team-`2DC432GLL2` binary (a bare `cua_node/bin/node` suffices — the id need not be `com.openai.codex`) the service answers the ping. So a single team-`2DC432GLL2` ancestor is sufficient.

    Why it broke and the fix. `ditto` copies ChatGPT.app's Developer ID `codex` into the bundle, but `sign_helpers` then re-signed it ad-hoc (to restore allow-jit after item 9), which also dropped team `2DC432GLL2`. Since `codex` is `node_repl`'s parent, that left no trusted ancestor → reject. Keeping OpenAI's Developer ID signature on `codex` and `codex-code-mode-host` preserves **both** the `allow-jit` / `allow-unsigned-executable-memory` entitlements (item 9's concern) **and** team `2DC432GLL2` (this one). `install/mac/install.sh`'s `sign_helpers` now re-signs only `codex_chronicle` and `rg`; the bundle re-seal signs `Codex++-bin` and the outer bundle without `--deep`, so the nested Developer ID Mach-Os are untouched. `codesign --verify --strict` passes with Developer ID nested binaries inside the ad-hoc bundle. Verified on the running install: after restoring `codex`/`codex-code-mode-host` from ChatGPT.app (identical version 26.901.51231, so same code, just the Developer ID signature back) and re-sealing, `codex` runs as team `2DC432GLL2`, the app launches with no integrity/`CodeRange` error, and the probe against the (untouched, pristine Developer ID) service answers the ping for a team-`2DC432GLL2` ancestor. The external service is never modified; stock ChatGPT's Computer Use is unaffected.

    Dead ends recorded so the wheel is not reinvented: the external service cannot be debugged (`lldb` attach dies with "lost connection" even non-hardened with `get-task-allow`; it uses a `sysctl` `KERN_PROC`/`P_TRACED` anti-debug), and patching its async/inlined verdict inside `ComputerUseIPCServer.start` was attempted (identity-extractor rewrite at `0x10016f608`; forcing the team-compare branch at `0x100179eb0` → `0x100179f0c`) but is unnecessary given the ancestry fix. A patched service *could* be shipped if ever needed — an ad-hoc re-sign with **only** `com.apple.security.application-groups` (not the provisioning-backed `application-identifier` / `keychain-access-groups` / `team-identifier`, which cause `RBSRequestErrorDomain Code=5` / POSIX 163) launches and binds the socket — but the Codex++-side signature fix is the correct one.
